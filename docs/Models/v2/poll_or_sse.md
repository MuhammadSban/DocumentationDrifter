# Poll visibly now, add SSE hints later

**Recommendation: build option A, a 5-second poll of our own server, and only while the console tab is visible.** Don't build SSE for v2. You asked whether server push is the better choice. For this system it isn't yet, and four reasons specific to the setup decide it. First, the only thing SSE buys is about **2.5 s on average and 5 s at worst**, and that is smaller than the noise around it: GitHub Actions start-time spikes measured in minutes, an unpublished Railway wake time with possible 502s, and the 28 s redeploy that your own pushes set off. Second, **SSE still needs the same list-runs endpoint** for first load and for catching up after sleep, redeploys or lost events, so it is option A plus a second delivery path. Third, on the pinned stack SSE means a new `async def` streaming route, thread-to-event-loop fan-out, a uvicorn shutdown flag, a hand-rolled framing layer (or a dependency pin that pip silently breaks), and a rewrite of the `ui.py` dev proxy, which currently never delivers a single event. It also can't be tested with `TestClient`. Fourth, **every push to this repo's main redeploys Railway about 28 s after the Action posts**, which cuts every open SSE stream at exactly the moment a run has just arrived. A short poll doesn't notice the redeploy. Both options share two problems the earlier discussion missed: an open tab keeps the Free-plan container awake and spends the $1 monthly credit, and a Railway volume turns every redeploy into downtime. That second problem is a reason to prefer the evidence-repo option for durable runs. The earlier "not yet" stands, with one correction to its latency table, given below.

Labels used throughout: **[M]** measured in this project (docs/Models/v2/README.md, 2026-10-18), **[S]** sourced, **[E]** estimate or inference.

## SSE saves 2.5 seconds inside a budget that swings by minutes

The earlier table said polling takes about 7–15 s and SSE about 5–10 s. The shape is right, but the framing needs tightening. Both rows are **[E]**: the v2 Action's 5–10 s push-to-result has not been measured, and only its parts have. Runner start was **2–4 s in 6 runs [M]**, the direct POST answered in **0.37 s [M]**, and the Action's health-check step and any setup steps sit on top of that unmeasured. Short polling adds a uniform 0–5 s plus one round trip, and SSE adds about one round trip. The honest statement is **"polling = SSE + 0–5 s (mean ≈ 2.5 s)" [E]**, so polling's range is really about 5–15 s rather than starting at 7 s ([polling notes, derived from WHATWG/MDN mechanics](https://html.spec.whatwg.org/multipage/server-sent-events.html)).

That 2.5 s sits beside much larger variance. In 2026 GitHub reported a start-delay incident where about **23% of runs were delayed by an average of 11 minutes** ([GitHub Status](https://www.githubstatus.com/incidents/fw294tth5m8y)) and another where **4.5% of all runs started more than 5 minutes late** ([GitHub Status](https://www.githubstatus.com/incidents/g6ffrm0rfvz9)). In the August 6–7 outage, some push events were **never processed and cannot be replayed** ([IncidentHub](https://blog.incidenthub.cloud/github-actions-pages-outage-aug-6-2026), secondary source). No source publishes a normal-day p95 for `ubuntu-latest` queue time, so the 2–4 s sample is best read as a typical median. On Railway's side, a sleeping service wakes on the first request, takes "a small amount of time", and that first request **"may return a 502 Bad Gateway"** ([Railway Docs: Serverless](https://docs.railway.com/deployments/serverless)). Railway publishes no wake-time figure. A lost push event or a slow wake is fixed by the console re-reading a list. A push stream alone doesn't fix either one.

Product practice points the same way. Vercel's published deploy-status component polls every **10 s** ([Vercel Platforms docs](https://vercel.com/platforms/docs/platform-elements/blocks/deploy-popover)). GitLab polled job status every 30 s through ETag-cached endpoints before moving one header to WebSockets. That change was worth it at about **45.7 M calls a day** ([GitLab blog](https://about.gitlab.com/blog/how-we-supercharged-gitlab-ci-statuses-with-websockets/)), roughly six orders of magnitude above a one-developer console.

## SSE costs a streaming stack this codebase doesn't have

Option A is one more plain sync `def` route next to the existing ones. It runs through `ui.py` unchanged, because each response is short and finite, and it tests with `TestClient` like every other route. Option B touches five places. The table compares the two on this stack (fastapi 0.115.6, starlette 0.41.3, uvicorn 0.34.0).

| | A: visible-tab poll, 5 s | B: SSE |
|---|---|---|
| Added delivery latency | 0–5 s, mean 2.5 s **[E]** | ~1 RTT **[E]** |
| New dependencies | none | none if hand-rolled; `sse-starlette<=3.0.2` pin or FastAPI ≥0.135 upgrade otherwise **[S]** |
| Server code | sync `GET /system/runs` + ETag | the same list route, plus an `async def` stream, a subscriber registry, loop fan-out, heartbeats, a shutdown flag |
| `ui.py` dev proxy | works as is | must be rewritten to stream, or bypassed with CORS **[S]** |
| Tests | `TestClient` | `TestClient` hangs; needs a real uvicorn thread plus a timeout guard **[S]** |
| Redeploy (no volume) | invisible; next poll hits the new container | every stream cut at swap; reconnect + re-fetch **[S/E]** |
| Cold-start 502 | next poll retries | EventSource gives up; manual retry code needed **[S]** |
| Railway edge exposure | ms-long requests, far from every limit | 15 min cap, 5 min idle, unconfirmed buffering/early-close reports **[S]** |
| Keeps Free container awake | while a tab polls | while a stream is open (heartbeats are outbound traffic) **[S]** |

**The thread trap.** Every route here is a sync `def`, and Starlette drives a sync generator through `iterate_in_threadpool`, which holds one of AnyIO's **40** default worker threads during each `next()` ([starlette/concurrency.py](https://github.com/encode/starlette/blob/0.41.3/starlette/concurrency.py); [AnyIO docs](https://anyio.readthedocs.io/en/stable/threads.html)). In experiments on the pinned stack, **40 blocking sync SSE streams hung every other sync route, `POST /system/analyze` included, and the threads stayed pinned after all 40 clients disconnected**. AnyIO can't interrupt a thread blocked in `queue.get()` (research experiment; mechanism per [starlette/responses.py](https://github.com/encode/starlette/blob/0.41.3/starlette/responses.py)). The SSE route therefore has to be the app's only `async def` route. The sync analyze handler would push into per-subscriber `asyncio.Queue`s through `loop.call_soon_threadsafe` with a loop captured at startup, use bounded queues and snapshot iteration, and run an `asyncio.wait_for(q.get(), 15)` heartbeat. The research verified this pattern on the pinned stack. It is correct, but it is new concurrency code in an app that currently has none, and it works only while there is exactly one uvicorn process.

**The dependency trap.** FastAPI 0.115.6 has no native SSE. Native support arrived in **0.135.0 (2026-03-01)** and requires `starlette>=0.46.0`, so using it means a framework upgrade ([FastAPI SSE docs](https://fastapi.tiangolo.com/tutorial/server-sent-events/); [PyPI](https://pypi.org/project/fastapi/0.135.0/)). Running `pip install sse-starlette` next to the pin resolves to **3.0.3**, which declared its Starlette floor incorrectly and **upgrades Starlette past FastAPI's `<0.42` cap**. You would have to pin `sse-starlette<=3.0.2` ([PyPI history](https://pypi.org/project/sse-starlette/#history)). Given AGENTS.md's minimal-dependency rule, the hand-rolled `StreamingResponse` with explicit `Cache-Control: no-cache` and `X-Accel-Buffering: no` headers is the only acceptable route, which means owning the framing and keep-alives yourself.

**Shutdown, the proxy and tests.** With its default `timeout_graceful_shutdown=None`, uvicorn 0.34.0 **waits indefinitely** on SIGTERM for open streams to finish. An experiment with three open streams was still running 12 s after SIGTERM ([uvicorn/server.py @0.34.0](https://github.com/encode/uvicorn/blob/0.34.0/uvicorn/server.py)). Your start command would need `--timeout-graceful-shutdown`. Railway's default 0 s drain SIGKILLs the old container anyway, so the flag matters as soon as anyone sets `RAILWAY_DEPLOYMENT_DRAINING_SECONDS` ([Railway Variables](https://docs.railway.com/reference/variables)). `ui.py`'s `urlopen(...).read()` never returns on an SSE body. The 180 s timeout applies per socket operation, so 15 s heartbeats keep resetting it. Each tab then pins one relay thread indefinitely and the browser never gets headers ([urllib docs](https://docs.python.org/3/library/urllib.request.html#urllib.request.urlopen)). Starlette's `TestClient` and httpx's `ASGITransport` both buffer the whole body before returning, so **any test that touches an infinite SSE route hangs CI** ([starlette/testclient.py](https://github.com/encode/starlette/blob/0.41.3/starlette/testclient.py); [httpx #1787](https://github.com/encode/httpx/discussions/1787)).

## Redeploys and Railway's edge hit streams, not short polls

This is the part specific to this project. A push to the repo's own main triggers the Action **and** a Railway redeploy. Both measured timings from 2026-10-18 are marked [M]:

```
t (s)  0      2–4         ~5–10 [E]            ~28 [M]                    +30 s … +3 min
       push ─► runner ─► health ─► POST 0.37 s [M] ─► run saved on OLD container
       push ─► Railway build ──────────────────────────► new container live (no volume: no gap [M])

Poll tab   sees run at POST + 0–5 s ──────────── next poll lands on new container, nothing to handle
SSE tab    event at POST + ~RTT ─────────────── stream cut at swap → reconnect → must re-fetch list
No volume  run file lives on the old container's disk → gone at swap (Action artifact is the only copy)
Volume     old container stopped BEFORE new one starts → polls and reconnects 502 for 30 s–3 min [S, anecdotal]
```

At cutover Railway sends SIGTERM with a **0 s default drain before SIGKILL** ([Railway Deployments](https://docs.railway.com/reference/deployments); [Variables](https://docs.railway.com/reference/variables)), and its own SSE guide warns streams "can still drop… such as deploys" ([Railway SSE guide](https://docs.railway.com/guides/sse-vs-websockets)). An event published in the old container's memory never reaches a tab that reconnects to the new one. Under the HTML spec, a reconnect that gets a **non-200 response "fails the connection" and EventSource stops retrying** ([WHATWG §9.2](https://html.spec.whatwg.org/multipage/server-sent-events.html)). A 502 during a gap or a cold wake therefore leaves the console silently dead unless you write your own retry loop. A poller absorbs the same 502 as one failed tick.

The edge adds further SSE-only risk. The documented limits are a **15-minute cap per request and a close after 5 minutes without data**, with WebSockets exempt ([Railway Specs & Limits](https://docs.railway.com/networking/public-networking/specs-and-limits)). A February 2026 staff reply described a 15-minute idle gap after the Fastly rollout ([Station](https://station.railway.com/questions/edge-proxy-logs-sse-silent-disconnects-d3c72731)). Several 2026 community threads remain **unconfirmed and unresolved**: a FastAPI/uvicorn SSE response delivered as one buffered body after 69 s ([Station](https://station.railway.com/questions/sse-streaming-responses-buffered-entirel-5b2916c5)), buffering until EOF that staff could not reproduce ([Station](https://station.railway.com/questions/edge-proxy-buffers-streaming-responses-4084b96c)), streams closed early after 60 s and 7 s despite 15 s heartbeats ([Station](https://station.railway.com/questions/premature-sse-socket-closures-across-pro-a121268c)), and responses with no bytes cut at about 60 s ([Station](https://station.railway.com/questions/edge-kills-requests-with-no-response-byt-c65210de)). None of these is proven, but each one is something you would have to rule out, and none of them can affect a millisecond-long poll. On connection caps, Railway accepts HTTP/2 from browsers, but the docs don't say which protocol the edge uses to reach the container. Uvicorn 0.34.0 speaks **HTTP/1.1 only** ([uvicorn 0.34.0](https://pypi.org/project/uvicorn/0.34.0/)), and `ui.py`'s `BaseHTTPRequestHandler` defaults to HTTP/1.0. Over HTTP/1.1, browsers allow **6 connections per origin across all tabs** ([MDN EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)), so the seventh local dev tab with SSE stalls every request from that origin. Production over HTTP/2 most likely avoids this, but that is unverified for your domain.

## Both options drain the Free credit; the volume adds downtime

**An open tab keeps the service awake no matter which option you pick.** Railway decides sleep from outbound packets only. Responses count as outbound, and the service sleeps 5–10 minutes after its last one ([Railway Serverless](https://docs.railway.com/deployments/serverless)). A 5 s poll and an SSE heartbeat both qualify, so a forgotten background tab keeps the container running around the clock. From Railway's RAM price of $0.00000386/GB-s ([pricing](https://railway.com/pricing)), being always awake costs about **$0.17/day at the 0.5 GB cap, so the $1 credit lasts about 6 days**. At a more realistic ~150 MB process it is about $0.05/day, or roughly 3 weeks, before any CPU cost **[E]**. (The research note's "roughly 3 days" overstates the drain about 2×. The conclusion still holds: always-on exceeds the $1/month Free credit unless RAM stays under about 100 MB.) The research did not establish what Railway does when the credit runs out. The fix is the same for both options: do nothing while `document.visibilityState !== 'visible'`. Browsers throttle hidden-tab timers anyway, down to **once per minute** under Chrome's intensive throttling ([Chrome Developers](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)), so a hidden tab polling every 5 s was never actually getting 5 s updates.

**A volume works against this repo's redeploy pattern.** Attaching one means "a small amount of downtime" on every redeploy, "even if there is a healthcheck", because Railway stops the old deployment before starting the new one ([Railway Volumes](https://docs.railway.com/reference/volumes)). Users report gaps of **30 s–1 min** ([Station](https://station.railway.com/questions/tips-for-reducing-deploy-downtime-bd119dd4)) and **2–3 min** ([Station](https://station.railway.com/questions/application-gets-sigterm-before-next-dep-dd6f2617)). Railway staff suggested moving storage to a separate service to keep zero-downtime deploys. Your own pushes redeploy within about 30 s of the Action's POST, so with a volume the measured **28 s no-downtime redeploy [M] would become a regular outage window**, and an Action that starts late in GitHub's tail would post into it. This favours the roadmap's **evidence repo** (runs written through GitHub's Contents API behind `runs.py`), which keeps deploys zero-downtime. Three design notes follow, all **[E]**, because the research did not cover the Contents API. The evidence repo must not be a watched or deployed repo, or each write starts a push loop. The service should keep an in-memory per-repo index, rebuilt from the evidence repo at startup and updated on `save`, so that polls never call GitHub. Contents API write latency and rate limits still need measuring. If you do choose the volume, size the Action's health-check retries to cover at least **3 minutes** of 502/503s. Size them that way regardless, because the same retries absorb cold wakes.

## Polling done well, in this codebase

Server: one sync route, `GET /system/runs?repository=owner/a&repository=owner/b&since=<cursor>`, so each tick is a single request for the whole watch list. It answers from the in-memory index described above and returns runs newer than the cursor, newest first. The cursor is the run's creation time, or `analysis_id` if IDs are ordered. The route also sets a weak `ETag` derived from each repo's latest run ID and returns **304 with no body** when `If-None-Match` matches. That is GitLab's pattern of "304 without hitting the database" ([GitLab polling docs](https://docs.gitlab.com/development/polling/); [MDN conditional requests](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Conditional_requests)). Optionally, send a `Poll-Interval` header so the server can slow clients down. Client: replace `setInterval` with a jittered `setTimeout` of 5 s ±15%. On `visibilitychange` to hidden, clear the timer. On visible, poll immediately and then resume. On a network error or 5xx, back off 5→10→20→60 s with jitter and reset after a success, following Brooker's guidance on retries ([AWS Builders' Library](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter)). On page load, fetch without a cursor to get history, which is the v3 run-history feature you are pulling forward anyway. Also retire the console's 300 s anonymous `api.github.com` poll and its self-triggered `POST /system/analyze` for repos the Action covers; otherwise each push gets analysed twice. Load estimate **[E]**: 720 requests/hour per visible tab, mostly 304s of a few hundred bytes. That is negligible for CPU and for egress at $0.05/GB.

**Migration path, with nothing thrown away.** If push is ever wanted, add `GET /system/events` as a thin signal carrying only `{repository, id}`, never the run itself. The client's only reaction is to run the same poll right away. The list endpoint stays the source of truth for first load, reconnects, redeploys and lost events. If the stream drops, the console falls back to the 5 s poll it already has. The SSE `id:` can be the cursor, so `Last-Event-ID` maps straight onto `?since=` ([Railway SSE guide](https://docs.railway.com/guides/sse-vs-websockets)).

## Conclusion

The question isn't really "poll or push". It is whether the console reads from a durable, listable store of runs. Both options depend on that store, and once it exists, polling is a thin client over it while SSE is a second, fragile path to the same data. In this setup the forces that actually shape what you see are your own redeploy pattern, Railway's sleep and edge behaviour, and GitHub's start-time tail. All of them punish long-lived connections and leave a short poll untouched. The decision that matters most for v2 is therefore choosing the evidence repo over the volume, because that choice decides whether your own pushes cause an outage.

Revisit SSE if any of these changes. Analyses become long-running and you want streamed progress rather than one finished run. Viewers grow to dozens of tabs at once, where request volume, not latency, starts to count. You move to an always-on paid host where sleep and credit stop mattering, and you confirm HTTP/2 end to end. Or you upgrade to FastAPI ≥0.135 for other reasons, which makes native SSE cheap. Even then, add it as the "something changed" signal on top of the list endpoint, not in place of it.

Every vision diagram that covers delivery has results leave the tracker only when someone asks for them (GET responses, inspection of the evidence repo) or through GitHub’s PR and commit comments, and none draws the tracker → browser connection SSE would need. The spec agrees: the viewer only has to show saved results and history, notifications are the first thing to cut, and hard real-time response is out of scope. So for v2 the console should poll a run-history endpoint while the tab is visible, keep runs in a separate evidence repo as M1 shows, and treat live push updates as a future scope change.
